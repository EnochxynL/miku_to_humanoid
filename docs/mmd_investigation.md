# MMD 调查笔记

从旧仓库 `docs/reference_recipes.md` 中抽出的 MMD 相关记录，保留当时的诊断数据与结论。

## 附加：把 MMD 模型（glTF/GLB）接进 GMR

输入是一份 MMD 模型转出的 GLB（`archived/py_mmd_anim/assets/星穹铁道—黑塔2.glb`）：
511 关节的 MMD 骨架（日文骨名、含 IK 骨）、一段 320 帧 @30 fps 的舞蹈、米制尺度。

### 两步转换

| 步骤 | 工具 | 说明 |
|---|---|---|
| GLB → BVH | `src/reference_maker/mmd_glb_to_bvh.py` | 只导出 GMR 需要的 14 根骨及其祖先链（29 关节）；输出 LAFAN1 约定：**Z-up、厘米、`LeftFoot`/`LeftToe` 命名** |
| BVH → pkl | `src/reference_maker/gmr_mmd_driver.py` | 在 GMR 环境里跑，**按我们的骨骼重算旋转偏移**后再 IK |

骨名映射：`腰→Hips`、`上半身2→Spine2`、`左足/左ひざ/左足首/左つま先→LeftUpLeg/LeftLeg/LeftFoot/LeftToe`，右同。

### 一个必须跨过的坑：GMR 的 lafan1 配置带 LAFAN1 专用的旋转偏移

直接喂我们的 BVH，重定向会**塌掉**（实测：骨盆 z 0.065 m、脚 −0.447 m）。
原因是 `bvh_lafan1_to_g1.json` 里每根骨有 `rot_offset`（例如脚是 −90°X），那是按 LAFAN1
的骨骼静止帧调好的；我们的骨头静止帧接近单位旋转，套上就扭成折叠姿势。

驱动脚本的解法：

```
target = R_human * offset   =>   offset = R_human_rest^-1 * R_robot_rest
```

用我们的骨骼参考帧与机器人零位姿态逐骨重算。修正后同一帧的骨盆落在 **0.755 m** ✓。

### 结果与限制

| 检查 | 结果 |
|---|---|
| GLB → BVH | 320 帧 / 10.6 s / 29 关节；GMR 读取后髋 1.008 m、直立 ✓ |
| 重定向（修正偏移后）| 骨盆 0.755 m，姿态合理 ✓ |
| 转成 clip | 2917 帧 / 5.83 s，骨盆 0.46–0.68 m，关节 ±1.8 rad，无 NaN ✓ |
| **模仿** | ❌ **安全包络触发**（机身倾到 45°）|

原因是这段舞蹈**几乎没有支撑相**：按脚高重新推导接触，flight 占 62–83%；
即使强制"始终有一只脚为支撑"，MPC 仍然在中途倒下。

**结论**：GLB → GMR → clip 这条链已经打通并验证，但"腾空型舞蹈"不是当前 MPC 能模仿的
输入（它要求接触相）。可选的下一步是把它约束成"贴地版"（始终踩地、只做上身动作），
那是参考层的改写，不是重定向问题。

### 数值诊断：几何是对的，**重定向的腿是错的**

用权威的 PMX 骨架（`pmx-mjcf` 的 `examples/heita/skeleton.json`，613 骨 bind_position）做两层核对。

**A1 几何**：我们 GLB 的 14 根映射骨与 PMX 的成对距离矩阵对比（距离与坐标系/镜像无关）

| 指标 | 结果 |
|---|---|
| 可比骨 | 14 / 14 |
| 相对误差 | 中位 **2.0%**、p90 9.0%、最大 17.3%（腰↔上半身2）|

→ **GLB 的骨架几何是正确的**，转换没问题。

**A2 重定向保真度**：把人类骨位（缩放 0.9、以髋为原点）与 G1 对应链接的 FK 位置逐帧比对

| 骨 | 中位误差 |
|---|---|
| 腰 | 0.000 m（对齐基准）|
| 上半身2 | 0.24 m |
| 肘 / 腕 | 0.35–0.56 m |
| 膝 | 0.67–0.80 m |
| **踝** | **1.14–1.30 m** |

踝-髋相对高度信号与人类的相关性只有 **0.15**；而且 G1 的脚会抬到离地 **0.52 m**，
而人类踝最高只有 0.25 m。→ **腿完全没有跟上**，问题在 GMR 这一层，不在转换。

### 顺带修掉一个真 bug：`convert_gmr` 的双支撑裁剪

```python
double = np.flatnonzero(support.all(axis=1))
first = int(double[0])      # 第一次双脚同时接触
dense = dense[first:]       # ← 前面全部丢弃
```

走路片段从双支撑开始是对的。但这支舞 83% 帧是腾空，第一次双支撑出现在 **4.1 s**，
于是 10.7 s 的动作被悄悄替换成"从中途开始的 5.8 s 片段"——这正是"看着完全不对"的一部分。

修复：只有当 `first` 落在开头 0.5 s 内才裁剪，否则保留原起点。
修复后同一输入的 clip 从 2917 帧 / 5.83 s 变成 **4984 帧 / 9.97 s**（与 10.7 s 的源按比例吻合）。

### 下一步（未做）

腿对不上，最可能是 IK 配置里 **`pos_offsets`**（pelvis `[0,0,-0.12]`、ankle `[0,0.07,0]` 等）
同样是按 LAFAN1 的骨骼帧调的。驱动脚本目前只重算了 `rot_offsets`；下一步应把 `pos_offsets`
也按我们的骨骼重算（用静止帧的骨长比例），再逐肢体核对误差是否落到 0.1 m 量级。

## 更正：`gmr_mmd_driver.py` 的偏移推导是错的，已弃用

用同一个驱动去跑**已知正确**的 LaFAN1 走路 BVH，与 GMR 原版 CLI 的输出对比：

| 项 | 结果 |
|---|---|
| dof 平均绝对差 | **0.53 rad** |
| dof 最大差 | **3.35 rad** |

一个让走路都崩掉的驱动，不能用来判断 MMD 的重定向。错因很清楚：`offset = R_human_rest^-1 · R_robot_rest`
里的 `R_human_rest` 取的是**动画第 0 帧**，而那是迈步中的姿态，不是骨骼的静止（bind）姿态；
拿它当参考基准，等于把整段动作的朝向偏移了一个姿态。

**结论：不要用运行时改偏移的办法。** GMR 的每个 `ik_match_table` 都是针对**某一种人类骨骼**标定的
（LAFAN1 的骨帧约定），换骨骼必须**为其建立一份新的 IK 配置**——正是 `gmr-newrobot-kit` 干的事：
用 bind pose 的骨长与静止朝向推导 `pos_offsets` / `rot_offsets`，而不是用第一帧动画去拟合。

### 已知边界（实测）

| 尝试 | 结果 |
|---|---|
| 原版 CLI + 自带 lafan1 配置 | 塌陷（骨盆 0.065 m、脚 −0.447 m）|
| 运行时改 rot_offsets（本驱动）| 连走路都崩（0.53 rad 偏差）→ **弃用** |
| 位置任务为主、朝向权重置零 | 骨盆高度正常（0.65–0.85 m），腿部相关性从 0.15 升到 0.54，但仍未达可用 |

人类腿长 0.88 m（髋 1.0 m、踝 0.12 m），G1 腿长 0.65 m：任何重定向都必须靠**屈膝**补偿，
因此"脚达不到人类踝位置"是物理限制，不是 bug；但当前结果的混乱程度远超这一限制所能解释，
仍指向"IK 配置与骨骼不匹配"。

## 突破：MMD 骨骼接进 GMR 的正确方式——**位置驱动**

### 症状与误导

把 MMD 骨架按 LaFAN1 拓扑、Y-up 厘米导出后，GMR 的重定向仍然是"腿交叉、躯干恒定歪向一侧"。
为此我做了几轮错误尝试，值得记下来：

| 尝试 | 结果 |
|---|---|
| 运行时重算 `rot_offsets` | 连走路都崩（0.53 rad 偏差）|
| 用 bind pose 推偏移 | 生成的偏移全变 identity，观感无变化 |
| 怀疑左右手认错 | 数据否定：LeftUpLeg x=+0.079、RightUpLeg x=−0.061 ✓ |
| 怀疑 GLB 旋转是 Z-up | 错：四元数按 (x,y,z,w) 读才对，骨 Y 轴与髋→脊柱方向只差 12.6° ✓ |
| 借 LaFAN1 骨长 | 骨架散架（LaFAN1 的骨沿 +X 排列）|

另外浪费了两轮：**多个残留的 MuJoCo 窗口同名**，导致"改了参数却没变化"的假象。
后来用"同数据跑两次 IK 比 qpos"（差 1.09 rad）才确认参数是生效的。

### 真正的发现

GMR 的配置里权重是这样分配的：

| 链接 | [位置权重, 朝向权重] |
|---|---|
| pelvis / 髋 / 膝 | `[0, 10]` ← **只有朝向** |
| 踝 | `[50, 10]` |
| torso / 肩 | `[0, 100]` ← **只有朝向** |
| 肘 / 腕 | `[0, 10]` ← 只有朝向 |

也就是说 **GMR 几乎完全靠"骨朝向"驱动**，而"人类骨帧 ↔ 机器人链接帧"的对应关系里有一个
绕骨轴的自转**在几何上不可观测**（转动它不改变任何位置），GMR 作者对每种源格式都是手工标定的。

绕开办法：**把权重反过来**——用人类关节**位置**驱动（位置是可信的），朝向权重置零。

```python
pos = {'pelvis':100, 'left_hip_yaw_link':60, 'left_knee_link':60, 'left_ankle_roll_link':60,
       'right_hip_yaw_link':60, 'right_knee_link':60, 'right_ankle_roll_link':60,
       'torso_link':100, 'left_shoulder_yaw_link':80, 'left_elbow_link':60,
       'left_wrist_yaw_link':40, ...}          # 每个 entry 的 [1]=pos_weight, [2]=0
```

配合按**关节锚点**（而不是链接原点）算出的比例表：

| 骨 | 人类距离 | 机器人距离 | 比例 |
|---|---|---|---|
| Spine2 | 0.216 | 0.309（肩关节）| 1.55 |
| LeftArm | 0.308 | 0.309（肩关节）| 1.35 |
| LeftLeg | 0.470 | 0.455（膝关节）| 0.97 |
| LeftFoot | 0.896 | 0.749（踝关节）| 0.84 |

结果（`runtime/gmr_clips/herta_dance/signals.npz`，4984 帧 / 9.97 s）：

| 指标 | 值 |
|---|---|
| 骨盆高度 | **0.744–0.931 m**（站立区间）|
| 最低脚 | 0.037–0.176 m |
| 支撑帧比例 | L 19% / R 21% |

观感：机器人**站起来了**，躯干、四肢朝向正常，不再是"缩成一团"或"恒定歪一侧"。
