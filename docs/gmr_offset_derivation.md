# GMR 偏移（rot_offset）成因排查

> 目标：回答"全身扭转、连 rest 朝向都要调参，是不是 bug"。本轮不靠观感，全部用可复现的测量。

## 1. GMR 这一层的真实语义（代码审计）

| 事实 | 位置 |
|---|---|
| 配置里 `rot_offset` 读入即 `R.from_quat(rot_offset, scalar_first=True)`，**标量在前 (w,x,y,z)** | `motion_retarget.py:129` |
| 目标朝向 = `R_human · rot_offset`，即偏移在**人骨局部坐标系**里右乘 | `offset_human_data()` |
| 配置坐标系为 **Z-up**（`ground = ground_height * [0,0,1]`）| `motion_retarget.py:85` |
| 每个任务 = mink `FrameTask(position_cost, orientation_cost)`，同一条人骨同时给位置和朝向 | `setup_retarget_configuration` |
| **仓库里没有任何推导/标定 `rot_offset` 的工具** | 全库 grep `calibrat/align_vectors/rot_offset` 无生成器 |

出厂 `bvh_lafan1_to_g1.json` 的权重分布：pelvis/髋/膝/肘/腕 `[0,10]`，踝 `[50,10]`，躯干/肩 `[0,100]`——**几乎纯朝向驱动**，位置只在踝。

因此：偏移是**逐 (源骨架, 机器人) 手工给出**的常量。SMPL-X 有 17 份配置、LaFAN1 有 8 份，都是各自标的。这解释了"为什么换骨架感觉要重调"——但**不代表只能靠肉眼**。

## 2. 本轮做的测量与结论

### 2.1 数据本身是自洽的（排除"导出坏了"）

| 检查 | 结果 |
|---|---|
| GLB bind pose 的骨朝向 | 全部 `[0,0,0]` ✓ |
| BVH 中骨朝向 vs GLB 的世界朝向（逐帧对比）| **0.0°** ✓ |
| GLB 里"髋→脊柱"位置方向 vs 该骨局部 Y 轴 | 差 **12.6°** ✓ 自洽 |
| BVH 中 `LeftUpLeg` / `RightUpLeg` 的 x 坐标 | `+0.079` / `−0.061` ✓ 左右没认错 |
| pybvh / MuJoCo 渲染 | 骨架站直 ✓ |

### 2.2 `rot_offset` 是不是可以推导：能，但要选对方程

| 推导方式 | 目标误差（目标朝向 vs 人骨）| 说明 |
|---|---|---|
| 用户手调值 | 57.8° | 早期在四元数顺序有 bug 时调的 |
| **指向轴（distal）几何推导** | **4.6°** | 每根骨用"链接指向子链接"的局部轴 → 人骨"指向子骨"的局部轴 |
| bind pose 全对应（`C = R_bind⁻¹·R_rest`）| 88.2° | **错**：bind pose 与机器人 rest 是两个不同姿态，强行对应把 88° 的差烘焙进去 |
| mesh PCA 求指向轴 | 54.4° | **错**：MJCF 的 body 原点在关节处，相邻原点仅 4.6–8 cm，PCA 主轴与骨方向不是一回事 |

### 2.3 "目标对了"≠"姿态对了"——本轮的负结果

用 distal 推导（目标误差 4.6°）渲染：机器人能站，但**手臂/脚的姿态仍然不对**。

逐帧量到的残差（frame 0）：

| 骨 | 目标误差 | 实际误差 |
|---|---|---|
| LeftUpLeg | 0.0 | 30.0 |
| LeftFootMod | 0.0 | 89.4 |
| LeftArm | 0.0 | 4.5 |
| LeftForeArm | 0.1 | 58.1 |
| RightForeArm | 0.1 | 95.1 |

放宽求解预算（`max_iter` 10→200，`damping` 0.5→0.05）后只从 40.8° 降到 38.7°——**已收敛**，不是算不够。

### 2.4 为什么"指向轴对了"还会歪：指向只定了 2/3 个自由度

`C` 是 3 个自由度。指向轴只约束 2 个，**剩下的滚转决定了子关节的弯曲平面**。滚转选错时，前臂够不到目标，求解器只能折中——这正是 35–140° 残差的来源。

补第二个轴（子关节铰链）的尝试：

| 做法 | 结果 |
|---|---|
| 机器人铰链轴 = 子关节 `xaxis` 在父链接局部系下的表示 | ✓ 可以直接拿到 |
| 人骨铰链轴 = 父→子相对旋转的转轴，在整段 clip 上加权平均 | ✓ 可以量出来 |
| 两轴正交化后构造 `C = B_human·B_robotᵀ` | **更差**（前臂 35°→140°）|

原因待查：MMD 骨的相对旋转不是纯铰链，平均出来的轴可能被其他分量的数值噪声主导；且符号需要按弯曲方向对齐。

### 2.5 又排除一个：转换器的左右手没问题

真正生成该 GLB 的工具是 `py_mmd_anim`（不是 `mmd2gltf-gui`；后者注释里写着
"position / normal : (x, y, z) -> (x, y, -z) …… rotations unaffected"，但**不是**产出该文件的工具）。
`py_mmd_anim` 的 Rust 端有 `Conversion::rotation` 与单测 `mirror_conjugation_flips_x_and_y`，
说明它会镜像旋转。

实测检验（绑定姿态，左右成对骨）：

| 检查 | 结果 |
|---|---|
| `R_right` vs `M · R_left · M`（M = diag(−1,1,1)）| **0.0°**（左腕/右腕、左ひじ/右ひじ、左足/右足、左ひざ/右ひざ、左足首/右足首）|
| 位置是否镜像 | 精确相等 ✓ |

→ **GLB 是自洽且正确镜像的**，转换器不是问题。

### 2.6 自动优化：能走到 ~30°，然后停住

把"各段指向一致性"当目标（与任何参考姿态无关），对 14 根骨的偏移做坐标下降：

| 阶段 | 平均指向误差 |
|---|---|
| 几何推导（起点）| 39.1° |
| 15° 网格一轮 | **29.4°** |
| 5° 网格两轮 | 30.8°（平台）|

同时放宽求解预算（`max_iter` 10→200、`damping` 0.5→0.05）只从 40.8 → 38.7°。
两者都说明：**这不是"还没调好"，而是这台机器人做不出这些姿态**。

具体证据（G1 的 MJCF）：`left_elbow_joint = 0` 时，上臂与前臂的实际夹角是 **75.8°**
（前臂朝侧面），而肘的下限只有 −60°——**手臂物理上伸不到人类那么直**。这类"零位姿态差异"
让任何"按 rest pose 推导"的常量都带进一个姿态误差。

逐骨残差（优化后）：

| 骨 | 目标误差 | 实际误差 |
|---|---|---|
| LeftArm / LeftUpLeg / LeftLeg | 2.6–4.1 | **3.4–14.9** ✓ |
| Hips / RightLeg / RightFootMod | 11.8–25.6 | 13–22 |
| LeftForeArm | 6.8 | 27.6 |
| **RightForeArm** | 1.9 | **101.9** ← 唯一大离群值，且与左侧严重不对称 |

右臂各关节**没有触限**（shoulder_pitch 10–29°、roll −35..−92°、elbow 0–11°，范围均有富余），
所以右前臂的问题不是限位，待查。

### 2.7 沿着"骨轴自转"扫描：也是平台（且更差）

以为瓶颈是滚转，就只扫这一个自由度（每根骨绕自己骨轴 0/45/…/315°）：

| 起点 | 结果 |
|---|---|
| 39.1° | **41.1°**（更差）|

说明"绕人骨轴向自转"不是正确的搜索方向——`C` 的自由度应在另一侧（机器人链接帧）或需要同时约束父子两轴。
滚转的做法本轮仍未成立，但**这条负结果排除了一个直觉上最像的解法**。

### 2.8 转换器的问题彻底排除（引擎源码为准）

`py_mmd_anim` 的 `src/bvh.rs` 里写得很清楚：

```rust
// MMD is left-handed (X right, Y up, Z toward the viewer) while BVH is right-handed.
// Re-labelling one axis (mirror_z, negate Z) rewrites the same physical pose in right-handed
// coordinates, so it applies as a *conjugation* to rotations and as a plain axis flip to positions.
position:  (x, y, z) -> (x, y, -z)
rotation:  (x, y, z, w) -> (-x, -y, z, w)   // "negates the quaternion x and y parts"
```

而实测 GLB 相对 VMD 的变换正是 `(-x, -y, z, w)`（上半身、上半身2、左ひじ三根骨逐一核对）。
**两者是配套的一对变换**（位置镜像 + 四元数 x/y 取负），不是混用。**数据端完全正确，我此前的判断是错的。**

### 2.9 剩下的精确问题：铰链是"关节级"约束，不能逐骨独立解

两轴推导失败的原因被自检暴露出来：

| 骨 | 指向轴误差 | 铰链轴误差 |
|---|---|---|
| 左前臂 | 0.0° | **32.2°** |
| 右前臂 | 0.0° | **133.2°** |
| 左臂 | 0.0° | 4.2° |

原因是**前臂的子关节是手腕**，而手腕的主要运动是**旋前旋后**——转轴几乎**平行于前臂自身指向轴**。
用平行轴构造坐标系是病态的（正交化后没有任何约束力），所以铰链项失效。

正确的提法是**关节级约束**（约束一对 C，而不是单根骨）：

```
对每个关节 j（父骨 p → 子骨 c）：
    C_p^-1 · Rel_human(t) · C_c = B_pc · Rot(axis_j, θ(t))
其中 Rel_human(t) = R_p(t)^-1 R_c(t)，B_pc 是机器人两个链接在零位时的相对朝向，
axis_j 是该关节在父链接局部系下的转轴。
```

- 每根骨仍有 2 个自由度来自指向轴；
- 每个关节加 1 个约束（把父子的 C 绑在一起）；
- 参考姿态处各关节角 θ 未知，但只是每关节 1 个标量。

这是一个小型的、可解的方程组（约 12 骨 + 11 关节），但**必须联合求解**，逐骨独立推导在数学上就不成立——这正是今晚所有"逐骨推导"版本都停在 30–40° 的根源。

### 2.10 顺序求解扭转链：仍不收敛，说明系统本身不相容

按 2.9 的提法实现了一个顺序求解器（`fit_twist_chain.py`）：根骨先定，然后每根骨只搜它自己的扭转角，
使"父关节的相对旋转"尽量落在关节轴上。最优扭转下的**离轴残差**：

| 关节 | 离轴残差（最优扭转下）|
|---|---|
| 左/右踝（FootMod 的父关节）| 51.5 / 49.7° |
| 左/右膝 | 52.7 / 48.8° |
| 左/右髋 | 36.7 / 27.0° |
| 左/右肩（肘关节约束）| **14.4 / 15.7°** |

肩/肘只有 14–16°，说明手臂的提法基本成立；但膝/踝在 50° 左右——**无论怎么选扭转，
人类膝踝的相对旋转都不落在机器人对应关节的轴上**。

这意味着：**这套数据 + 这台机器人的关节轴系，不存在一组常量偏移能同时满足所有关节约束**。
换句话说，GMR 这种"每根骨一个常量旋转 + 每帧独立求 IK"的模型，对这台机器人是**欠定/不相容**的——
这也解释了为什么所有版本都停在 30–40°、且误差随动作幅度增长。
